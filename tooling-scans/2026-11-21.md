# Monthly tooling scan: 2026-11-21

Second scan in this series. The first was `tooling-scans/2026-09-19.md`, and
this report follows up on every item it left open.

Run in an ephemeral Linux cloud sandbox with no Apple Silicon, no MLX, no
Ollama, no GPU, and none of the private recordings in `~/.cache/allklaro`.
That split decides what could be measured here and what is handed off.

## Summary

The landscape moved more in these two months than the whole of the previous
scan, and it moved in the categories this sandbox cannot measure.

**Adopt-worthy, measured here:**

1. **The serving stack upgrade from the September scan was recommended and
   never landed.** `pyproject.toml` and `uv.lock` still carry FastAPI
   0.139.2, uvicorn 0.51.0, Starlette 1.3.1, and onnxruntime 1.27.0.
   Upstream is now FastAPI 0.165.0, uvicorn 0.54.0, Starlette 1.10.0, and
   onnxruntime 1.32.0. The repo's non-integration suite gives **identical
   results on both**: 767 passed, 36 skipped. Separately, the pinned Silero
   graph produces **bit-identical** per-frame scores under onnxruntime
   1.27.0 and 1.32.0, and `wordfreq` returns identical values under numpy
   2.4.6 and 2.5.5, so the two upgrades with real behavioral surface are
   both equivalence-checked rather than merely green. **ADOPT.**

2. **The httpx2 WATCH item resolves cleanly, with no application changes.**
   September flagged `StarletteDeprecationWarning: Using 'httpx' with
   'starlette.testclient' is deprecated; install 'httpx2' instead` as
   something to track. httpx2 2.16.2 now exists, and adding it alongside
   httpx makes Starlette's test client pick it up on its own: the suite
   stays at 767 passed and 36 skipped, and the warning count drops from 1 to
   **0**. The app keeps httpx for Ollama. **ADOPT** as a `dev` group
   addition.

**NEEDS LOCAL BENCHMARK**, in priority order:

- **`gemma4:12b` against `gemma3:12b`.** Gemma 4 did not exist at the last
  scan and now does, in E2B, E4B, 12B, 26B-A4B, and 31B, under **Apache 2.0**
  rather than Gemma 3's custom Gemma Terms of Use. `gemma4:12b` is a direct
  size-tier swap for the current main model. This is the single highest-value
  thing on the list, and it carries a specific trap documented below.
- **`parakeet-mlx` 0.5.2 to 0.7.0.** Three releases shipped since September.
  The API this project calls is unchanged, verified by source diff, and 0.7.0
  adds **word boosting**, which maps directly onto the dialect mishearing
  problem catalogued in `dialects.txt`.
- **Qwen3.5 for the draft slot.** Released February 2026, Apache 2.0, in
  0.8B, 2B, 4B, 9B, 27B, and larger.
- **Qwen3-ASR**, carried over unresolved from September.

**No regression risk was found this month.** The two pins that September
recommended both landed in `b97e92c`, and both are still correct: py3langid
is still at 0.4.0 upstream, so `<0.4` holds, and Silero 6.2.3 ships weights
**byte-identical** to the pinned 6.2.2, so the checksum pin needs no touch.

Measured here, on the repo's own fixtures and test suite: the serving stack
at both version sets, the httpx2 migration, onnxruntime equivalence on the
pinned Silero graph, `wordfreq` stability across numpy versions,
`fasttext-langdetect` against the project's labeled detection fixture, the

Not measured here, and not guessed at: anything through MLX, Ollama, or the
private recordings. That is all of the translation model work and most of the
ASR work. Those carry a runnable spec instead of a number.

Two honest limits on the numbers below. First, the suite run reports **2
failed** in both arms, `tests/test_speakers.py::test_embed_*`, because the
optional `speakers` extra (speechbrain and torchaudio) is not installed in

model. That is an artifact of the venv, identical in both arms, and it does
not affect the comparison. It is also not a discovery: the CI workflow's own
comment already states that `speakers` "is optional to the app but not to

results short of it for one known and documented reason. Second, the VAD
equivalence check runs on a
deterministic synthetic signal, not speech. That is a valid use of synthetic

Dependencies were installed only into throwaway venvs under the scratchpad.
`pyproject.toml`, `uv.lock`, and application code were not touched, and this

## Constraints applied

A candidate had to be free and open to use, runnable locally on Apple
Silicon and fully offline, privacy-preserving, free of Java or other heavy
runtimes, and a plausible improvement on the incumbent in accuracy, latency,
footprint, or maintenance.

Rejected on those rules this month, without further evaluation:

- **`nvidia/canary-1b-v2`** and the rest of the Canary family. Credible
  multilingual ASR with real adoption, but it runs under the NeMo toolkit,
  which drags in PyTorch and a large framework, and no MLX port exists.
  Fails the heavy-runtime rule and the Apple Silicon rule together.
- **`nvidia/parakeet_realtime_eou_120m-v1`**, which looked promising as a
  turn-taking and end-of-utterance detector (p50 160 ms EOU latency) and
  would have been interesting next to the VAD. It is **English only**, which
  ends it for a German and Spanish app, and it needs NeMo 2.5.3+, and it
  ships under the NVIDIA Open Model License rather than a standard open
  license.
- **`translategemma`**, unchanged since the last scan, still built on Gemma 3,
  and already rejected in `README.md` for ignoring saved corrections and
  style steering. Nothing has changed that.
- Cloud-only and API-gated models, including Qwen3-ASR-Flash, on the offline
  and privacy rules.

LanguageTool stays exactly where it is, an opt-in extra behind `ALLKLARO_LT=1`,
because of the Java rule. No grammar or spelling tool is proposed.

## Translation models

**Current:** Ollama, main model `gemma3:12b`, draft model
`qwen2.5:7b-instruct` (`server.py:421`, `static/app.js`).

Nothing here is testable in this sandbox: no Ollama, no Apple Silicon, no
GPU, and no access to the corrections history or recordings the probe suite
scores against. No numbers are offered.

**Research.** The September report stated "No Gemma 4 exists." That is no
longer true, and it is the headline change this month. Gemma 4 shipped in
2026 in five variants, E2B, E4B, 12B Unified, 26B-A4B (mixture of experts),
and 31B Dense. Verified against primary sources: the Gemma 4 model card
states "Apache 2.0" and "maintains multilingual support in over 140
languages," and the Hugging Face API reports `license:apache-2.0` on
`google/gemma-4-12B-it`. Ollama carries a `gemma4:12b` tag at roughly 7.7 GB
with a 256K context window.

Two things make this worth real attention rather than a routine look.

**The license improves.** Gemma 3 is distributed under Google's custom Gemma
Terms of Use, which is source-available rather than open source. Gemma 4 is
Apache 2.0. For a project whose standing rule is "free and open to use,"
moving the main model from a custom license to Apache 2.0 is a win
independent of any quality change.

**The size tier matches exactly.** `gemma4:12b` sits where `gemma3:12b`
sits, so the RAM tier table in `README.md` does not have to be redrawn for
the swap to be testable. That is unusual, and it is why this outranks the
Qwen candidates.

Qwen3.5 (February 2026, Apache 2.0) is the other credible family, in 0.8B,
2B, 4B, 9B, 27B, 35B-A3B, 122B-A10B, and 397B-A17B. Its interest here is the
**draft slot**, not the main slot: the bar for a draft is to beat
`qwen2.5:7b-instruct`'s 1.5 s without falling below its 18/22, which the 4B
and 9B sizes could plausibly do at a smaller footprint.

**Recommendation: NEEDS LOCAL BENCHMARK.** License, offline story, runtime,
and language coverage all pass. Only the thing that matters is unverified,
and it is unverifiable here: whether the model keeps being AllKlaro.
`README.md` already records that every model tried so far that was better at
translation was worse at this job, so general multilingual strength is not
the question.

Spec for the Mac, main model first:

```
ollama pull gemma4:12b
RUN_INTEGRATION=1 ALLKLARO_MODEL=gemma4:12b uv run pytest -m integration -v
uv run python tools/replay.py --audio ~/.cache/allklaro/<recording>.m4a
uv run python tools/trace_report.py
```

Then the draft slot:

```
ollama pull qwen3.5:4b
RUN_INTEGRATION=1 ALLKLARO_MODEL=qwen3.5:4b uv run pytest -m integration -v
```

Metrics and baselines, from the 2026-07-27 table in `README.md`, measured on
an M4 Max with 48 GB: `gemma3:12b` scores **22/22** at **2.1 s** warm
translation and keeps every learner feature, `qwen2.5:7b-instruct` scores
**18/22** at **1.5 s**, and `translategemma:4b` scores **17/22** at **1.0 s**.
A candidate has to reach 22/22 to displace `gemma3:12b` as main, because the
four probes the 7B loses (Berlin flavor, correction steering, and gender
overrides) are the features rather than the polish.

**Three cautions for whoever runs this, in order of how much time they will
save.**

First, and this one will bite: **`server.py` disables thinking mode by model
name, and `gemma4` is not in the list.** Four sites
(`server.py:2180`, `:2212`, `:2498`, and `:2592`) do
`if any(k in model.lower() for k in ("qwen3", "deepseek-r1", "gpt-oss")):
body["think"] = False`. Gemma 4 ships configurable thinking modes, so a
`gemma4:12b` run under the current code may think on every request, which
would show up as a large latency regression and possibly as reasoning text
leaking into cards. Add `"gemma4"` to that tuple **in a scratch edit** before
believing any `gemma4` timing. Do not read a slow first result as a verdict
on the model.

Second, the opposite is true for Qwen3.5 and is free: `"qwen3"` is a
substring of `"qwen3.5"`, so `qwen3.5:*` already matches that check and
already gets `think: False`. No change needed.

Third, the `README.md` warning about two-model setups still applies, and it
is sharper at the 12B tier. A resident draft model once made Ollama unable to
load `gemma3:12b` at all. Check `ollama ps` and watch for `refine_ms` pinned
at exactly `REFINE_TIMEOUT_SEC`, which is the signature of the refine pass
silently never landing.

## Fast partial ASR

**Current:** `parakeet-mlx` 0.5.2 (Apache-2.0), model
`mlx-community/parakeet-tdt-0.6b-v3` (`server.py:1356`).

**Maintenance check.** This is the one incumbent that has genuinely moved.
September recorded 0.5.2 as the newest release. Three have shipped since:
**0.5.3** (2026-10-01), **0.6.0** (2026-11-02), and **0.7.0** (2026-11-04).

**Tested here**, to the extent it can be: the sdists for 0.5.2 and 0.7.0
were downloaded from PyPI and diffed. MLX itself cannot run in this sandbox,
so this is a source and API comparison, not a behavioral one.

The result is good news for upgrade risk. Every call this project makes is
unchanged:

| call site | 0.5.2 | 0.7.0 |
|---|---|---|
| `from parakeet_mlx import from_pretrained` | present | present |
| `from parakeet_mlx.audio import get_logmel` | `get_logmel(x, args)` | `get_logmel(x, args)` |
| `model.generate(mel)` | `generate(self, mel, *, decoding_config=DecodingConfig())` | identical |
| `model.preprocessor_config` | present | present |

The package's exported names are also unchanged, and `pyproject.toml`
differs only in the version string. The one new module is additive:
`parakeet_mlx/boost.py`. So `transcribe_partial` (`server.py:1388`) should
work untouched on 0.7.0.

**What 0.7.0 adds that matters to this project.** `boost.py` is a word
boosting (keyword biasing) layer, composable through `boost.words(...)`,
`boost.scale`, `boost.combine`, and `boost.lift`, applied during **beam**
decoding. Upstream's own example shows a word going from "fronts" to
"trunks" with a 4.0 boost. 0.7.0 also extends beam decoding from TDT to
RNNT models.

That is interesting here for a specific reason rather than a general one.
This project maintains `dialects.txt`, `glossary.txt`, and
`tools/dialect_mishearings.py`, which is a catalogue of exactly the failure
class word boosting exists to fix: a known word that the model does not
produce because it is rare in its training distribution. A boost list built
from the project's own glossary is a much more direct instrument than
prompting is.

The catch, and it is a real one: boosting works under beam decoding, and the
partial pass is the most latency-constrained path in the app. Parakeet is
there because it is roughly 12x faster than Whisper on the same window (71 ms
against 884 ms, per the comment at `server.py:1340`). Beam decoding is
slower than greedy by construction, so this could easily cost more than it
returns on partials.

**Recommendation: NEEDS LOCAL BENCHMARK.** Two separate questions, worth
running in order, because the first is cheap and the second is only worth
doing if the first passes.

```
# 1. Is 0.7.0 a free upgrade at greedy decoding? (scratch venv, not the project)
uv pip install 'parakeet-mlx==0.7.0'
uv run python tools/partial_headroom.py --audio ~/.cache/allklaro/<recording>.wav
uv run pytest tests/test_partial_asr.py -v
```

Metric and baseline: the headroom figure that harness already reports for
`parakeet-tdt-0.6b-v3` at 0.5.2. The accumulation lag it measures is about
65% of first-word lag at p50, so a slower partial model costs more than
accuracy gains are likely to return. If headroom holds and
`tests/test_partial_asr.py` is green, 0.7.0 is an ordinary maintenance
upgrade and can land on that basis alone.

```
# 2. Only if (1) passes: does boosting pay for beam decoding on partials?
#    Build the boost list from the project's own lexicons, then compare
#    greedy against beam-with-boost on the same audio:
uv run python tools/dialect_mishearings.py
uv run python tools/partial_headroom.py --audio ~/.cache/allklaro/<recording>.wav
```

Metrics: recovered mishearings from `tools/dialect_mishearings.py` against
its current count, traded against the headroom number from step 1. A boost
configuration that fixes dialect words but pushes partial latency past the
budget in `PROGRESS.md` is a regression, because partials exist to make the
app feel responsive. Note upstream's own caveat that booster state does not
carry across chunks, which matters for a chunked partial pass. Worth saying
plainly: this second step is a feature evaluation, not a version upgrade,
and it may be worth doing on the **final** Whisper pass instead, where the
latency budget is looser and the dialect words actually need to be right.

## Speech recognition

**Current:** `mlx-whisper` 0.4.3 (MIT), model
`mlx-community/whisper-large-v3-turbo` (`server.py:396`).

**Maintenance check.** 0.4.3 is still the newest release on PyPI, still
uploaded 2025-08-29, so it has now gone roughly 15 months without a release.
Meanwhile `mlx` itself is at 0.32.4 (2026-10-14). `mlx-whisper` declares
`mlx>=0.11` with **no upper bound**, so pip and uv will happily install
0.4.3 against any future MLX.

That combination is worth naming as a risk even though nothing is broken: a
package that has not been released in 15 months, pinned open against a
dependency that ships monthly, is where a silent break eventually arrives.
It cannot be checked here, because MLX does not run in this sandbox.

**Candidates.** No new multilingual ASR worth the switch appeared. There is
no Whisper large-v4, no Qwen3.5-ASR, and no Parakeet v4: `nvidia/parakeet-tdt-0.6b-v3`
and `mlx-community/parakeet-tdt-0.6b-v3` are still the current multilingual
Parakeet. Qwen3-ASR remains the one real candidate, unchanged since
September, Apache-2.0, in 0.6B and 1.7B, with MLX quantizations now showing
meaningful adoption (`mlx-community/Qwen3-ASR-0.6B-8bit` at roughly 174k
downloads, `Qwen/Qwen3-ASR-1.7B` at roughly 1.6M).

One forward-looking item, flagged rather than recommended. The Gemma 4 model
card states that **E2B, E4B, and 12B Unified accept audio input** natively.
A single model doing both ASR and translation would be a large architectural
simplification for this app. It would also collapse the pipeline that
`PROGRESS.md` documents in detail, discard the partial and final split that
makes the app feel fast, and there is no evidence it would be better at
either job. **WATCH**, worth a curiosity probe the next time someone has
`gemma4:12b` pulled anyway, not a plan.

**Recommendation: NEEDS LOCAL BENCHMARK** for Qwen3-ASR (carried over
unchanged), plus **WATCH** on `mlx-whisper` staleness.

Spec for the Mac, unchanged from September:

```
uv pip install mlx-qwen3-asr            # into a scratch venv, not the project
uv run python tools/dump_transcripts.py --audio ~/.cache/allklaro/<recording>.wav \
    --out /tmp/whisper_baseline.jsonl
# then the same recording through Qwen3-ASR-1.7B, and:
uv run python tools/boundary_quality.py --dump /tmp/whisper_baseline.jsonl
```

Metric and baseline: transcription quality on the same 54-minute recording
that produced the existing figures, against `whisper-large-v3-turbo`. The
decisive cases are the dialect ones in `tools/dialect_mishearings.py` and
`dialects.txt`, not aggregate WER, because a model that wins on WER while
losing dialect mishearing recovery is a downgrade for this app. Record warm
per-chunk latency too, against the budget in `PROGRESS.md`.

The `mlx-whisper` staleness check is a one-liner worth running at the same
time, since it needs no new downloads:

```
uv run python -c "import mlx.core, mlx_whisper; print(mlx.core.__version__)"
RUN_INTEGRATION=1 uv run pytest -m integration -k whisper -v
```

If that is green on current MLX, the risk is theoretical and the note can be
dropped. If it is not, the fix is a pin, and this scan found it before a
`uv sync` did.

## Voice activity detection

**Current:** Silero VAD (MIT), v6.2.2 ONNX weights under `onnxruntime`
1.27.0, pinned by tag and SHA-256 (`server.py:474-477`), with an
energy-based fallback.

**Upstream:** `silero-vad` is at **6.2.3** (2026-09-23), four days after the
last scan. Still MIT.

**Tested here.** The 6.2.2 and 6.2.3 wheels were pulled from PyPI and every
shipped model file hashed.

| file | 6.2.2 SHA-256 (first 8) | 6.2.3 SHA-256 (first 8) | identical |
|---|---|---|---|
| `silero_vad.onnx` | `1a153a22` | `1a153a22` | yes |
| `silero_vad.jit` | `e1122837` | `e1122837` | yes |
| `silero_vad_16k_op15.onnx` | `7ed98ddb` | `7ed98ddb` | yes |
| `silero_vad_16k_sequence.onnx` | `9ccdacc4` | `9ccdacc4` | yes |
| `silero_vad_half.onnx` | `1e0b195a` | `1e0b195a` | yes |
| `silero_vad_op18_ifless.onnx` | `7671cd04` | `7671cd04` | yes |
| `silero_vad_openvino_16k.onnx` | `7776b81a` | `7776b81a` | yes |

Every model file in 6.2.3 is byte-identical to 6.2.2. The 6.2.3 release
changes packaging, not weights. `SILERO_SHA256` in `server.py` is
`1a153a22f4509e...`, which matches, so the pin is correct and needs no edit.
This is the pin from September doing exactly its job: the question "did the
weights move?" took one command to answer with certainty instead of a
guess.

**Also tested here:** whether the onnxruntime upgrade in the serving stack
changes VAD behavior. The pinned graph was run over 400 frames of a fixed,
seeded, deterministic signal under both runtimes, with single-threaded
session options.

| onnxruntime | mean score | score digest | voiced at 0.5 | CPU |
|---|---|---|---|---|
| 1.27.0 (locked) | 0.001582859 | `442230db2773722b` | 0.0% | 211.3 us/frame |
| 1.32.0 (current) | 0.001582859 | `442230db2773722b` | 0.0% | 183.0 us/frame |

The two score arrays are **bit-identical**, `numpy.array_equal` true with a
maximum absolute difference of 0.0, and 1.32.0 is about 13% cheaper per
frame. Per-frame cost remains irrelevant either way: a 512-sample frame at
16 kHz is a 32,000 us budget, so both use well under 1% of one core.

The near-zero voiced fraction is the synthetic signal being rejected, which
reproduces the September finding that v6 rejects this kind of harmonic buzz,
and it must not be read as anything about speech. The value of this test is
only the equivalence: upgrading onnxruntime does not perturb the detector
that the hysteresis thresholds in `SileroScorer` (0.35 continuing, 0.5
starting) are tuned against.

**Recommendation: NO CHANGE** to the VAD itself, and the onnxruntime half of
the stack upgrade is cleared to land. The September local-benchmark spec is
still the right procedure if the thresholds are ever re-tuned or a future
release changes the weights, and is not repeated here since nothing has
changed to trigger it.

## Language detection

**Current:** `py3langid` 0.3.0 (BSD-3-Clause), pinned `>=0.3.0,<0.4` since
`b97e92c`, restricted to the active language pair and combined with a
lexical vote (`server.py:2868-2887`).

**Maintenance check.** py3langid upstream is still 0.4.0, so the pin holds
and the breaking change it guards against is unchanged. `lingua` is still
2.2.0, so the September WATCH has nothing new to report.

**Candidate: `fasttext-langdetect` 1.2.0** (MIT, 2026-10-27), not previously
evaluated. It wraps Meta's fastText `lid.176` language ID model. Two things
make it a serious candidate rather than a curiosity: version 1.2.0 ships as a
**pure `py3-none-any` wheel** depending only on numpy and requests, reading
the fastText binary format itself with `struct` and numpy, so there is no
compiled extension and no Apple Silicon wheel question at all; and it offers
a compressed model variant under 1 MB.

**Tested here** against `tests/fixtures/detect_phrases.py` (202 phrase cases
and 46 trap cases after `cases()` expands across pairs) through the server's
own `detect_language`, replacing only `_langid_vote` and leaving the lexical
vote in place. That is the same methodology the September report used for
lingua, and the same numbers `tests/test_detect.py` gates on.

| configuration | PHRASES | TRAPS | model vote | cold start | RSS | on disk |
|---|---|---|---|---|---|---|
| py3langid 0.3.0 (incumbent) | **99.0%** | **97.8%** | 65.1 us | 0.05 s | 100 MB | 0.73 MB |
| fasttext-langdetect, `lid.176.bin` | 99.5% | 95.7% | 161.6 us | 0.09 s | 202 MB | 125.2 MB |
| fasttext-langdetect, `lid.176.ftz` | **100.0%** | 95.7% | 171.7 us | 0.49 s | 89 MB | 0.89 MB |

The incumbent row reproduces the 99.0% and 97.8% recorded in both
`test_detect.py`'s comment and the September report, which is the check that
these measurements are wired up correctly.

The compressed `.ftz` row is the interesting one, and it is better than it
looks on two axes at once: a **perfect** `PHRASES` score with zero misses,
at **89 MB** resident against the incumbent's 100 MB, and 0.89 MB on disk
against 0.73 MB. It is about 2.6x slower per vote, which does not matter on
this path: `_langid_vote` runs on typed text, once per message, not per audio
frame, so 172 us is invisible next to a human typing.

**But it loses on TRAPS, and that is the half that counts.** It misses two
trap cases where the incumbent misses one. The fixture's own docstring says
TRAPS is the adversarial half that exists to stop the word-list vote being
weighted any higher, so a loss there is not a rounding error in kind, even
when it is small in size. The new miss is `de-en` on "Ist that so", an
English sentence stuffed with German function words, which is precisely the
failure mode the fixture was built to catch.

**Be candid about the size of these differences.** TRAPS has 46 cases, so
one case is worth 2.2 points; PHRASES has 202, so one case is worth 0.5. The
entire measured difference between the incumbent and the `.ftz` candidate is
**two phrase cases won and one trap case lost**. That is not a result that
can bear much weight in either direction, and nobody should read "100.0%
versus 99.0%" as a meaningful accuracy gain on a 202-case set.

**Recommendation: NO CHANGE**, and this is the third candidate in a row to
produce the same shape of result. lingua in September scored +0.5 on PHRASES
and -2.1 on TRAPS. fasttext-langdetect scores +1.0 on PHRASES and -2.1 on
TRAPS. Two independent detectors landing on the same trade is informative:
the incumbent's pairing of a small character n-gram model with a lexical
vote is already well matched to this workload, and the remaining PHRASES
misses ("Na klar", "Bien hecho") are not going to be fixed by swapping the
model without giving up trap robustness.

**WATCH, narrowly.** The one configuration worth remembering is
`fasttext-langdetect` with `lid.176.ftz` as a **replacement for lingua** on
the September WATCH list, not as a replacement for py3langid. It beats lingua
on every axis that made lingua interesting (same TRAPS score, better PHRASES,
89 MB against 20 MB resident but 0.89 MB against 305.9 MB on disk, pure
Python with no compiled extension) so if the TRAPS cases are ever handled
another way and a model swap becomes attractive, this is the better candidate
to revisit. Two operational notes for that day: it downloads its model from
`dl.fbaipublicfiles.com` on first use, which is the same one-time-fetch
pattern as Silero and would want the same tag-and-checksum treatment, and its
default cache is the system temp directory, so `FTLANG_CACHE` would need to
point at `~/.cache/allklaro`. The `lid.176` model is also under CC-BY-SA, not
MIT like the wrapper, which is a weaker license than the incumbent's
BSD-3-Clause.

## Word frequency

**Current:** `wordfreq` 3.1.1 (Apache-2.0).

3.1.1 remains the newest release, still uploaded 2023-11-21. As September
recorded, this is a deliberate sunset rather than neglect: the maintainer
stopped updating the data because generative AI polluted the open web corpus
it drew on. No freely available, offline, comparable-coverage replacement
surfaced this month either.

**Tested here.** September named the real risk as packaging rather than
data, a frozen package breaking against a future numpy. That is now checkable
against the numpy the stack upgrade would bring, so it was checked:
`zipf_frequency` was sampled across eleven German, Spanish, and English words
including a dialect-ish form (`gekickt`, 2.92) and a nonsense compound
(`Donaudampfschiff`, 0.0).

All eleven values are **identical** under numpy 2.4.6 and numpy 2.5.5.
The full suite also passes under 2.5.5.

**Recommendation: NO CHANGE.** The sunset is arguably a feature for this use
case: `zipf_frequency` is used to judge whether a word is common enough to
be worth surfacing to a learner, and a pre-2021 human-language snapshot is a
better instrument for that than a corpus contaminated with model output. The
packaging risk named in September is, for this numpy upgrade, measured and
absent.

## Serving stack

**Current (locked):** FastAPI 0.139.2, uvicorn 0.51.0 with `[standard]`,
Starlette 1.3.1, onnxruntime 1.27.0, numpy 2.4.6, httpx 0.28.1.

**Upstream now:** FastAPI 0.165.0, uvicorn 0.54.0, Starlette 1.10.0,
onnxruntime 1.32.0, numpy 2.5.5, httpx 0.28.1 (unchanged since 2024-12-06).

**Follow-up first.** September measured this upgrade, recommended **ADOPT**,
and it did not land. `b97e92c` carried only the two pins. `pyproject.toml`
and `uv.lock` are still at the old versions, so the gap is now larger than it
was: Starlette has gone 1.3.1 to 1.10.0 rather than 1.3.1 to 1.6.0. The
argument for taking it is unchanged and slightly stronger: staying close to
upstream so that a security fix is never a large jump.

**Tested here.** The repo's non-integration suite was run unmodified in
throwaway venvs under Python 3.12.

| stack | result |
|---|---|
| locked: fastapi 0.139.2, uvicorn 0.51.0, starlette 1.3.1, onnxruntime 1.27.0, numpy 2.4.6 | 767 passed, 36 skipped, 2 failed, 19.99 s |
| current: fastapi 0.165.0, uvicorn 0.54.0, starlette 1.10.0, onnxruntime 1.32.0, numpy 2.5.5 | 767 passed, 36 skipped, 2 failed, 18.49 s |
| current plus httpx2 2.16.2 alongside httpx | 767 passed, 36 skipped, 2 failed, 19.73 s |

The 2 failures are identical in all three arms and are the missing
`speakers` extra described above, not a stack regression. The 36 skips are
the MLX, Ollama, and recording-dependent tests, so this result covers the
HTTP and websocket layer thoroughly and the model layer not at all. Timing
differences across arms are noise on a shared sandbox and should not be read
as a performance result.

Two upgrades in that set have behavioral surface beyond "the suite is green,"
and both were checked separately rather than taken on trust: onnxruntime
1.32.0 computes **bit-identical** Silero scores (see the VAD section), and
numpy 2.5.5 gives **identical** `zipf_frequency` values (see the word
frequency section). Starlette 1.3.1 to 1.10.0 is the largest jump and the one
with the most surface area, and it passed with no application changes.

**Recommendation: ADOPT**, as ordinary maintenance. Re-run
`RUN_INTEGRATION=1 uv run pytest -m integration -v` on the Mac before landing,
since nothing here touches the model layer.

**The httpx2 WATCH item resolves: ADOPT.** September flagged
`StarletteDeprecationWarning: Using 'httpx' with 'starlette.testclient' is
deprecated; install 'httpx2' instead` as a thing to track so it would land as
a deliberate change rather than a broken suite. httpx2 2.16.2 is now
available, and the migration turns out to need **no application changes at
all**:

- Installing httpx2 **instead of** httpx fails immediately, as it should:
  `tests/conftest.py` and `server.py` both import `httpx` directly (the app
  needs it for Ollama), so the suite dies at collection with
  `ModuleNotFoundError: No module named 'httpx'`. httpx2 is a distinct
  package, not a drop-in rename.
- Installing httpx2 **alongside** httpx is the whole fix. Starlette's test
  client detects and prefers httpx2 on its own, the suite stays at 767 passed
  and 36 skipped, and `StarletteDeprecationWarning` occurrences go from 1 to
  **0** across the full run. `pytest -W error::DeprecationWarning
  tests/test_api.py` also passes clean, 36 passed.

So the action is to add `httpx2>=2.16.2` to the `dev` dependency group, next
to pytest, and leave `httpx` exactly where it is in the main dependencies.
Test-only change, no application code, and it retires the warning before a
future Starlette turns it into an error.

**Granian: NO CHANGE**, carried over. Granian 2.8.9 (BSD-3-Clause) is still a
credible Rust ASGI server and still passes the license and offline rules, but
the bottleneck in this app is ASR and LLM inference, not the ASGI layer.

## Candor about these findings

The honest shape of this month is that the measurable categories are all
healthy and the important news is in the categories this sandbox cannot
touch. Gemma 4 and parakeet-mlx 0.7.0 are the two findings most likely to
change the app, and this report contains **zero measurements** of either
one's behavior. What it contains instead is a license check, an API
compatibility diff from source, and a precise spec with a baseline, which is
what can be known from here.

What is solid: the Silero weight comparison and the onnxruntime equivalence
check are facts, both derived from hashing real artifacts and comparing real
arrays. The language detection numbers run the project's own fixture through
the project's own code path and reproduce the project's own recorded
baseline. The httpx2 result is a direct before-and-after on the project's
own suite. The parakeet API comparison is a source diff of the actual
published sdists, not a changelog reading, which matters because upstream
publishes no release notes.

What is weak, stated plainly: the language detection comparison turns on
three individual test cases out of 248, which is too thin to carry a
decision, and the report says NO CHANGE partly for that reason rather than
despite it. The suite results cover the HTTP and websocket layer and nothing
about the model layer, which is where this app actually lives. The VAD
equivalence check uses synthetic audio, which is appropriate for an
equivalence question and useless for an accuracy one. And the September
report's own caution still applies to this one: a scan that cannot see the
machine it is reporting on should be read with that in mind.

One process note worth recording. September's serving stack ADOPT was
measured, recommended, and then not landed, and this scan spent effort
re-measuring it at wider version gaps. That is cheap to repeat but not free,
and the gap grows each month it waits.

# Monthly tooling scan: 2026-09-19

First scan in this series, so there are no prior reports to follow up on and
no previously rejected options to avoid. Everything below is measured or
researched fresh.

Run in an ephemeral Linux cloud sandbox with no Apple Silicon, no MLX, no
Ollama, no GPU, and none of the private recordings in `~/.cache/allklaro`.
That split decides what could be tested here and what is handed off. It also
produced one wrong conclusion, corrected in place below and called out in
the closing section.

**Status:** both items this report recommends adopting outright landed on
`main` in `b97e92c` while the report was open for review.

## Summary

Two findings are worth acting on soon, and both are about dependency drift
rather than about a better tool existing.

1. **`py3langid` 0.4.0 is a breaking release, and the project does not pin
   against it.** `pyproject.toml` asks for `py3langid>=0.3.0` with no upper
   bound. 0.4.0 shipped on 2026-09-02 and removed
   `LanguageIdentifier.from_pickled_model`, which is exactly what
   `server.py:2818` calls. The server catches the failure and falls back to
   the word lists, so nothing crashes, but measured on the repo's own
   `tests/fixtures/detect_phrases.py`, detection drops from **99.0% to
   83.2%** on `PHRASES` and from **97.8% to 89.1%** on `TRAPS`. The
   regression reinstates precisely the failure class that fixture exists to
   guard ("Happy birthday!", "Merry Christmas!", "Take care" all misdetect
   again). `tests/test_detect.py` would go red, so CI catches it, but any
   fresh `uv sync` without the lockfile, or any lock refresh, walks into it.
   **ADOPT: pin `py3langid>=0.3.0,<0.4`.**

2. **The Silero VAD download URL points at a moving branch.**
   `server.py:455` fetches
   `.../silero-vad/raw/master/src/silero_vad/data/silero_vad.onnx`. Fetching
   a core model from a branch rather than a tag means two installs of the
   same commit can get different weights, with nothing in the tree recording
   which one a given machine cached. **ADOPT the pin** (a tagged URL plus a
   checksum).

   **Correction, added after this report was first written.** An earlier
   draft of this section claimed the project was tuned on Silero v5 and that
   new installs were silently drifting to v6. That was wrong, and the
   conclusion it drove was wrong with it. The repository's first download
   from `master` was in July 2026, by which point `master` already served
   the v6.2.x weights, so the app has been running v6 all along and its
   hysteresis thresholds are tuned on v6, not v5. Verified against upstream
   tags: `v6.2`, `v6.2.1`, and `v6.2.2` all ship a byte-identical
   `silero_vad.onnx` (`1a153a22...`), and only `v6.0` differs
   (`597d30b3...`). The error came from reading `SileroScorer`'s "v5 onnx
   interface" comment as a statement about which weights were in use; it
   describes the input signature, which v6.2.x preserves. There was no
   pending silent regression, and no v5-to-v6 decision to make. The
   moving-branch reproducibility risk was real, and is the part worth
   acting on.

Also adopt-worthy, lower stakes: the serving stack upgrade
(FastAPI 0.141.1, uvicorn 0.53.0, Starlette 1.6.0, onnxruntime 1.30.0)
passes the repo's full non-integration suite here, 671 passed and 34
skipped, with no code changes.

**NEEDS LOCAL BENCHMARK**, in priority order:

- Qwen3-ASR (Apache-2.0, released 2026-01-29, 0.6B and 1.7B, German and
  Spanish supported) via `mlx-qwen3-asr`, against `whisper-large-v3-turbo`.
- Translation main-model candidates that postdate the 2026-07-27 round:
  Qwen3 32B and Mistral Small 24B class models.

No category produced a candidate that is both clearly better and testable
here, so nothing is being recommended on research alone.

## What this sandbox could and could not do

Testable here, and actually tested: `py3langid` 0.3.0 and 0.4.0, `lingua`
2.2.0, Silero VAD v5 and v6 ONNX graphs under CPU `onnxruntime`, and the
FastAPI and uvicorn stack. The repo's own fixtures and test suite ran
unmodified, which is what makes these numbers trustworthy rather than
synthetic: `tests/fixtures/detect_phrases.py` is the project's own labeled
workload, and `python -m pytest` is the project's own gate.

Not testable here, and not guessed at: anything through MLX, Ollama, or the
private recordings. That covers most of the ASR and all of the translation
model comparisons. Those carry a runnable spec instead of a number.

One honest limit on the VAD work below. The repo ships
`tests/fixtures/real_conversation_voicing.json`, a per-frame voiced envelope
of a real 54-minute conversation, but it stores one bit per frame and no
audio, so it cannot be replayed through a different VAD. The v5-versus-v6
comparison here therefore runs on a deterministic synthetic signal, which
establishes that the two models behave very differently and what each costs
in CPU, but says nothing about which is more accurate on speech.

Dependencies were installed only into a throwaway venv under the scratchpad.
`pyproject.toml`, `uv.lock`, and application code were not touched, and this
PR contains only this report.

## Constraints applied

A candidate had to be free and open to use, runnable locally on Apple
Silicon and fully offline, privacy-preserving, free of Java or other heavy
runtimes, and a plausible improvement on the incumbent in accuracy, latency,
footprint, or maintenance. The Java rule is the reason LanguageTool stays
where it is, an explicitly opt-in extra behind `ALLKLARO_LT=1` rather than
anything closer to the default path, and it is why no grammar or spelling
tool is proposed here. Cloud-only and API-gated models were rejected on the
offline and privacy rules without further evaluation.

## Speech recognition

**Current:** `mlx-whisper` 0.4.3 (MIT), model
`mlx-community/whisper-large-v3-turbo` (`server.py:383`).

**Maintenance check:** 0.4.3 is still the newest release on PyPI, last
uploaded 2025-08-29. No upgrade is available, and none is pending.

**Candidate: Qwen3-ASR.** Apache-2.0, released 2026-01-29 by the Qwen team,
in 0.6B and 1.7B sizes, covering 30 languages including German and Spanish.
Apple Silicon access is through `mlx-qwen3-asr` (Apache-2.0, 0.4.3, uploaded
2026-09-19), and `mlx-audio` 0.5.4 (MIT) also lists Qwen3-ASR support.
Published comparisons claim it beats Whisper large-v3 on MLS, Common Voice,
and MLC-SLM, and third-party MLX numbers claim lower WER than
large-v3-turbo at lower peak memory. Those are vendor and third-party
claims, not measurements on this project's audio, and AllKlaro's workload
(conversational German with Hessisch and Worms dialect, three or more
speakers, short VAD-closed chunks) is far enough from those benchmarks that
the ranking should not be assumed to carry over.

**Recommendation: NEEDS LOCAL BENCHMARK.** The license, the offline story,
the runtime, and the language coverage all pass; only the accuracy claim is
unverified, and it is unverifiable here.

Spec for the Mac:

```
uv pip install mlx-qwen3-asr            # into a scratch venv, not the project
uv run python tools/dump_transcripts.py --audio ~/.cache/allklaro/<recording>.wav \
    --out /tmp/whisper_baseline.jsonl
# then the same recording through Qwen3-ASR-1.7B, and:
uv run python tools/boundary_quality.py --dump /tmp/whisper_baseline.jsonl
```

Metric and baseline: transcription quality on the same 54-minute recording
that produced the existing figures, compared against
`whisper-large-v3-turbo` as the incumbent. The decisive cases are the
dialect ones already catalogued in `tools/dialect_mishearings.py` and
`dialects.txt`, not aggregate WER, because a model that wins on WER while
losing "nett verstarne" style mishearing recovery is a downgrade for this
app. Also record warm per-chunk latency: large-v3-turbo currently sits
inside the budget documented in `PROGRESS.md`, and anything slower is a
regression regardless of accuracy. If Qwen3-ASR wins on both, re-run
`RUN_INTEGRATION=1 uv run pytest -m integration -v` before believing it.

## Fast partial ASR

**Current:** `parakeet-mlx` 0.5.2 (Apache-2.0), model
`mlx-community/parakeet-tdt-0.6b-v3` (`server.py:1336`).

**Maintenance check:** 0.5.2 is the newest release on PyPI, uploaded
2026-06-05. No upgrade available.

**Candidates:** Qwen3-ASR-0.6B is the only serious one, and it is
interesting here for the same reason it is interesting above, except that
the partial pass has a much harder latency constraint than the main pass.
Parakeet is a transducer that emits tokens as audio arrives, which is
structurally the right shape for this job; Qwen3-ASR is not obviously the
same shape.

**Recommendation: NEEDS LOCAL BENCHMARK, low priority.** The incumbent is
current, purpose-fit, and not obviously beaten. If the ASR benchmark above
is run anyway, the marginal cost of sizing the partial pass too is small:

```
uv run python tools/partial_headroom.py --audio ~/.cache/allklaro/<recording>.wav
```

Metric and baseline: the headroom figure that harness already reports for
`parakeet-tdt-0.6b-v3`. A candidate has to preserve or improve it; the
accumulation lag it measures is ~65% of first-word lag at p50, so a slower
partial model costs more than its accuracy gains are likely to return.

## Voice activity detection

**Current:** Silero VAD (MIT), v6.2.x ONNX weights under `onnxruntime`
1.27.0, downloaded once to `~/.cache/allklaro/silero_vad.onnx`, with an
energy-based fallback (`server.py:454-457`, `SileroScorer`). `SileroScorer`
calls this the "v5 onnx interface," which is accurate about the input
signature (`input`, `state`, `sr`) and says nothing about the weights;
v6.2.x keeps that signature.

**Upstream:** `silero-vad` is at 6.2.2 (uploaded 2026-09-17). v6.0 landed
2025-08-25, v6.2 on 2025-12-10, and v6.2.1 on 2026-02-24. Still MIT.

**Tested here.** Both the v5.1.2 and v6.2.2 `silero_vad.onnx` files were
pulled from their PyPI wheels, and the branch file was pulled by cloning the
upstream repo directly, since the sandbox proxy blocks raw GitHub reads.

The graph signatures are identical across versions, all three exposing
`input`, `state`, and `sr`, so `SileroScorer` detects `state` and takes its
v5 path on every one of them. Nothing breaks, which is precisely why the
swap is silent.

| model | SHA-256 (first 8) | signature | voiced on fixed synthetic input | CPU cost |
|---|---|---|---|---|
| v5.1.2 `silero_vad.onnx` | `2623a295` | `state` (v5 path) | 63.2% | 136.3 us/frame |
| v6.2.2 `silero_vad.onnx` | `1a153a22` | `state` (v5 path) | 2.0% | 137.4 us/frame |
| v6.2.2 `silero_vad_16k_op15.onnx` | n/a | `state` (v5 path) | 2.0% | 134.0 us/frame |

The file at `master`, which is what `server.py` downloads, hashes to
`1a153a22`. Checked against upstream tags, that same file ships at `v6.2`,
`v6.2.1`, and `v6.2.2` byte for byte, and only `v6.0` differs
(`597d30b3`). Since `master` has served `1a153a22` since the v6.2 release in
December 2025, and this project first downloaded in July 2026, `1a153a22` is
what every install of this app has been running. The v5 row below is
therefore the counterfactual, not the incumbent.

Per-frame CPU cost is effectively identical and irrelevant either way: a
512-sample frame at 16 kHz is a 32,000 us budget, so all three use about
0.43% of one core. Latency is not the story.

v5 and v6 agree on only 38.8% of frames on the same input, and the 16k op15
export agrees with the v6 default on 100% of frames, confirming those two
are the same model in two encodings. **The synthetic input is a harmonic
buzz, not speech, so 63.2% versus 2.0% must not be read as "v6 rejects
speech" or as "v6 is better at rejecting non-speech."** It establishes only
that v5 and v6 are materially different detectors, which matters here only
as background: the app runs v6 and always has. For scale, the real
conversation fixture records a voiced fraction of 82.69% over 101,878
frames, nowhere near the synthetic 63.2%, which is the clearest evidence
that the synthetic proxy does not stand in for speech.

**Recommendation: ADOPT a pinned download.** Fetching a core model from a
moving branch means two installs of the same commit can get different
weights, with nothing in the tree recording which. Pin the URL to a release
tag and verify a known SHA-256 after download. Because `1a153a22` is what
installs already cached, pinning to `v6.2.2` with that checksum is not a
behavior change for anyone: cached files match, so nothing re-downloads.

**No v6 migration benchmark is needed**, contrary to the earlier draft of
this report. There is no v5 install to migrate from. The local-benchmark
spec below is kept only for the case where the thresholds are ever re-tuned
or a future Silero release changes the weights again, since it is the right
procedure for that:

```
# current weights as the baseline, then the candidate, on the same real audio:
VAD_BACKEND=silero uv run python tools/replay.py --audio ~/.cache/allklaro/<recording>.m4a
uv run python tools/trace_report.py
uv run python tools/dump_transcripts.py --audio ~/.cache/allklaro/<recording>.wav --out /tmp/base.jsonl
uv run python tools/boundary_quality.py --dump /tmp/base.jsonl
```

Swap `~/.cache/allklaro/silero_vad.onnx` between the two weight files
between runs, keeping everything else fixed. Note that `load_silero()` now
checksums the cached file, so a hand-swapped model is replaced on the next
start unless `SILERO_SHA256` is changed to match it.

Metrics and baselines: voiced fraction against the fixture's **0.8269** over
**101,878** frames of the 54-minute Berlin recording; utterance count
against the **703** utterances, **522** of them German, recorded in
`tools/boundary_quality.py`; and the broken-boundary rate that same harness
reports for the soft-max and pause conditions. Then confirm `tests/test_vad.py`
and `tests/test_pace.py` still pass. The hysteresis thresholds in
`SileroScorer` (0.35 continuing, 0.5 starting) are tuned against the current
weights, so if a candidate looks worse at those values, re-tune before
concluding anything: the comparison worth making is tuned against tuned.

## Language detection

**Current:** `py3langid` 0.3.0 (BSD-3-Clause), restricted to the active
language pair, combined with a lexical vote (`server.py:2806-2848`).

**Tested here** against `tests/fixtures/detect_phrases.py` (101 phrases and
23 traps, expanded by `cases()` across every pair that contains the phrase's
language) using the server's own `detect_language`, so these are the same
numbers `tests/test_detect.py` gates on.

| configuration | PHRASES | TRAPS | latency | cold start | RSS | on disk |
|---|---|---|---|---|---|---|
| py3langid 0.3.0 (incumbent) | 99.0% | 97.8% | 75.3 us | 0.12 s | 63 MB | 0.78 MB |
| py3langid 0.4.0, as the code stands | 83.2% | 89.1% | 9.3 us | n/a | n/a | 4.64 MB |
| py3langid 0.4.0, method renamed | 99.5% | 95.7% | 732.3 us | 0.94 s | 138 MB | 4.64 MB |
| py3langid 0.4.0, renamed and pair cached | 99.5% | 95.7% | 42.1 us | 0.94 s | 138 MB | 4.64 MB |
| lingua 2.2.0, full accuracy | 100.0% | 95.7% | 49.1 us | 0.01 s | 20 MB | 305.9 MB |
| lingua 2.2.0, low accuracy mode | 97.5% | 97.8% | 41.2 us | 0.01 s | 20 MB | 305.9 MB |

The incumbent row reproduces the 99.0% recorded in `test_detect.py`'s own
comment, which is the check that these measurements are wired up correctly.

Three things in that table are worth reading carefully.

**The 0.4.0 row as the code stands is the breaking change.** 0.4.0 removed
`LanguageIdentifier.from_pickled_model`; `server.py:2818` calls it, the
`except Exception` catches the `AttributeError`, logs
"language model failed; falling back to word lists," and every detection
falls through to the lexical vote. The fast 9.3 us is just the word lists
being cheap, which is not a feature when they are 15.8 points less accurate.

**0.4.0 is not a free upgrade even once fixed.** The rename to
`from_model_file(MODEL_FILE, norm_probs=True)` restores the model and buys
+0.5 points on `PHRASES`, but it costs 2.1 points on `TRAPS`, roughly
doubles resident memory (63 MB to 138 MB), and adds 0.8 s to startup. It
also needs a second fix to be usable at all: `set_languages` costs 702.2 us
per call in 0.4.0 against roughly 60 us in 0.3.0, and `_langid_vote` calls
it on every single detection, which is where the 732.3 us comes from.
Caching the last-set pair brings it to 42.1 us, faster than the incumbent,
but that is two changes to land a mixed accuracy result.

**lingua is more interesting than its download size suggests.** At 305.9 MB
on disk it looks disqualifying for a local app, but it loads lazily per
language pair: building a German and English detector and classifying took
0.01 s and left resident memory at 20 MB, against py3langid's 63 MB. It
posts the only perfect `PHRASES` score. It is Apache-2.0, pure Python plus a
compiled extension, fully offline, and has no heavy runtime. It loses 2.1
points on `TRAPS`, and the traps are the adversarial half that the fixture's
own docstring says exists to stop the word-list vote being weighted higher,
so that loss is not a rounding error.

**Recommendation: ADOPT the pin, `py3langid>=0.3.0,<0.4`.** This is the
minimal correct action. It preserves the measured 99.0% and 97.8%, keeps the
lighter footprint, and closes a live hole in the dependency spec. Migrating
to 0.4.0 is **NO CHANGE** for now: it is a mixed result that costs two code
changes and 75 MB for no clear win, and there is no reason to take it while
0.3.0 is available and working.

**lingua: WATCH.** Worth revisiting if the `TRAPS` cases can be handled
another way, or if `PHRASES` misses start mattering more than trap
robustness. It should not be adopted on a 0.5-point `PHRASES` gain paid for
with a 2.1-point `TRAPS` loss. Note also that the lingua figures above route
through a replaced `_langid_vote` while leaving the lexical vote in place,
so a real adoption would want the confidence thresholds (`MODEL_CEILING`,
`LEXICAL_MARGIN`) re-tuned to lingua's probability scale rather than
inherited from py3langid's.

## Word frequency

**Current:** `wordfreq` 3.1.1 (Apache-2.0).

3.1.1 remains the newest release and was uploaded 2023-11-21. This is not
neglect, it is a deliberate sunset: the maintainer stopped updating the data
because generative AI polluted the open web corpus it drew on, and because
Reddit closed its public archives. The published frequencies are a snapshot
of human usage through roughly 2021 and are stated as unlikely to be updated
again.

No freely available, offline, comparable-coverage replacement surfaced.

**Recommendation: NO CHANGE.** The sunset is arguably a feature for this use
case. `zipf_frequency` is used here to judge whether a word is common enough
to be worth surfacing to a learner, and a pre-2021 human-language snapshot
is a better instrument for that than a corpus contaminated with model
output. The practical risk is packaging, not data: a frozen package can
break against a future Python or numpy. Nothing is broken now, and the full
suite passes here under numpy 2.4.6.

normal for that project's cadence and not a health signal either way.

Wiktionary edits for the cost of a download, with no code change and no
risk.

`StarletteDeprecationWarning: Using 'httpx' with 'starlette.testclient' is
deprecated; install 'httpx2' instead`. Nothing fails today, and this is a
test-only dependency, but it will eventually force a move to httpx2. Worth
tracking so it lands as a deliberate change rather than as a broken suite.

**Granian: NO CHANGE.** Granian 2.8.3 (BSD-3-Clause) is a credible Rust
ASGI server and passes the license and offline rules, but the bottleneck in
this app is ASR and LLM inference, not the ASGI layer, and uvicorn is not
the thing standing between a spoken word and a translated card. Swapping it
would trade a well-understood websocket path for a marginal gain in the one
place that is not the constraint.

## Translation models

**Current:** Ollama, main model `gemma3:12b`, draft model
`qwen2.5:7b-instruct` (`server.py:408`, `static/app.js:247`).

Nothing here is testable in this sandbox. There is no Ollama, no Apple
Silicon, no GPU, and no access to the correction history or recordings that
the project's probe suite scores against. No numbers are offered.

**Research.** No Gemma 4 exists; the Ollama library still lists Gemma 3 at
270M, 1B, 4B, 12B, and 27B as current. The `translategemma` family is
already evaluated and rejected in `README.md` for the documented reason that
it is a strict-translator fine-tune that ignores saved corrections and style
steering, and nothing has changed that. The credible candidates that
postdate the 2026-07-27 round are Qwen3 32B class models and Mistral Small
24B class models, both reported to translate German and English at or near
the top of the local field.

That reported strength is not the question, though. `README.md` already
records that `qwen2.5:32b-instruct` beat `gemma3:12b` on raw translation and
was still not the right main model, because it ignored injected dictionary
gender notes and would not write Wormser dialect. The bar is the 22-probe
integration suite, not translation quality in the abstract, and every model
tried so far that was better at translation was worse at being AllKlaro.

**Recommendation: NEEDS LOCAL BENCHMARK.** Spec for the Mac:

```
ollama pull qwen3:32b
RUN_INTEGRATION=1 ALLKLARO_MODEL=qwen3:32b uv run pytest -m integration -v
uv run python tools/replay.py --audio ~/.cache/allklaro/<recording>.m4a
uv run python tools/trace_report.py
```

Metrics and baselines, from the 2026-07-27 table in `README.md`, measured on
an M4 Max with 48 GB: `gemma3:12b` scores **22/22** at **2.1 s** warm
translation and keeps every learner feature; `qwen2.5:7b-instruct` scores
**18/22** at **1.5 s**; `translategemma:4b` scores **17/22** at **1.0 s**. A
candidate has to reach 22/22 to displace `gemma3:12b` as main, because the
four probes the 7B loses (Berlin flavor, correction steering, gender
overrides) are the features rather than the polish. For the draft slot the
bar is different and lower: beat `qwen2.5:7b-instruct`'s 1.5 s without
falling below its 18/22, which is what makes the smaller Qwen3 sizes worth a
look even if the 32B is not.

Two cautions for whoever runs this. Keep RAM tiers in mind, since the
README's recommendations are tier-specific and a 32B main model needs both
models warm. And `server.py:2130` already special-cases `qwen3` by
disabling thinking mode, so a Qwen3 candidate exercises a code path the
current default models do not.

## Candor about these findings

The two headline findings are dependency hygiene, not better tooling. That
is the honest result of this month's scan: the incumbents are in good shape,
mlx-whisper and parakeet-mlx are both at their newest releases, and the one
category where a genuinely promising new model appeared (Qwen3-ASR) is
exactly the category this sandbox cannot measure.

The language detection numbers are solid, because they run the project's own
fixture through the project's own code path and reproduce the project's own
recorded baseline. The serving stack result is solid for what it covers, and
covers nothing about the model layer. The VAD numbers are the weakest thing
here: the hash comparison and the signature check are facts, and the
frame-agreement figure is real but measured on synthetic audio, so it
supports "these differ materially" and nothing about which is better.

The VAD section is also where this report got something wrong on the first
pass, and it is worth naming rather than quietly patching. It claimed the
app was running Silero v5 and was about to drift to v6, when the app had
been running v6.2.x since July 2026. The bad inference was treating a code
comment about the ONNX input signature as evidence of which weights were
loaded, in a sandbox with no access to the cache that would have settled it.
The recommendation that survived (pin the URL) was right for a different
reason than the one first given: reproducibility, not a pending regression.
A scan that cannot see the machine it is reporting on should be read with
that in mind.

Everything sent to the Mac is sent because it could not be measured here,
not because it was measured and found ambiguous.
